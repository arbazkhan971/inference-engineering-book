# The GPU memory hierarchy in one page for inference engineers
researched: 2026-08-27 · researcher: glm-5.3-flash
## Key facts
- There are roughly four tiers of memory relevant to LLM serving, and they trade capacity against speed by orders of magnitude at each step: on-chip SRAM/registers (tens of MB, tens of TB/s), HBM on the GPU package (80–192 GB today, 3.35–8.0 TB/s), host RAM (hundreds of GB to multiple TB, order-of-tens-of-GB/s per socket over PCIe to the GPU), and NVMe SSDs (TBs, ~7 GB/s per PCIe 4.0 drive).
- H100 SXM5: 80 GB HBM3 at 3.35 TB/s, 50 MB of L2 cache (PCIe variant), 60 MB on the full GH100 die (NVIDIA H100 architecture whitepaper; Chips and Cheese H100 review, fetched 2026-08-27).
- H200 SXM: 141 GB HBM3e at 4.8 TB/s — nearly double H100 capacity, 1.4× its bandwidth (NVIDIA H200 datasheet, fetched 2026-08-27).
- B200 (Blackwell): 192 GB HBM3e at 8.0 TB/s (NVIDIA Blackwell datasheet, fetched 2026-08-27).
- AMD Instinct MI300X: 192 GB HBM3 at 5.3 TB/s peak theoretical (AMD MI300X product page and datasheet, fetched 2026-08-27).
- On-chip SRAM/L2 bandwidth is roughly an order of magnitude higher than HBM: H100's L2 is sized at 50–60 MB versus 80 GB of HBM — a ~1300:1 capacity gap between tiers (NVIDIA H100 whitepaper, fetched 2026-08-27).
- Decode is memory-bandwidth-bound: every generated token requires streaming the model weights from HBM once per batch, so single-stream token throughput scales with HBM bandwidth, not FLOPS. This is why H100 beats A100 on inference by more than the TFLOPS ratio suggests (A100 80 GB: 2,039 GB/s vs H100: 3,350 GB/s; computecomparison H100 page, fetched 2026-08-27).
- FlashAttention (arXiv:2205.14135, NeurIPS 2022) computes exact attention with no materialized N×N matrix by tiling Q, K, V into blocks that fit in SRAM, using the online-softmax trick; it reports wall-clock speedups (e.g., ~15% end-to-end training speedup on BERT-large and ~3× speedup on GPT-2 attention versus PyTorch baselines in the paper) and reduces attention memory from O(N²) to O(N) (arXiv:2205.14135, 2022).
- Roofline intuition: arithmetic intensity (FLOPs per byte moved) determines whether a kernel is compute-bound or memory-bound. Decode GEMV has intensity ~1 FLOP per weight byte; only large-batch prefill GEMMs approach the compute roof.

## How it works
- **The pyramid.** Registers and shared memory/SRAM sit inside each SM and run at tens of TB/s but total tens of MB. HBM is a stack of DRAM dies on the GPU package: GB-scale, a few TB/s. Host RAM attaches over PCIe (~tens of GB/s). NVMe is the cold tier. Each step down is ~10× slower per byte and ~1000× larger.
- **Why inference pays HBM transit every step.** During autoregressive decode, batch size is typically small, so weight matrices cannot be reused across enough tokens to amortize the read. Each decode step for a 70B model in FP16 must move ~140 GB of weights (70B × 2 bytes) from HBM to the compute units. On an H100 (3.35 TB/s) that floor is 140 GB ÷ 3.35 TB/s ≈ 42 ms per step — an upper bound of ~24 tokens/s per stream before any KV-cache or activation traffic. The formula: `max_decode_tokens_per_s ≈ HBM_bandwidth / bytes_of_weights_read_per_step`. Batching raises arithmetic intensity because one weight read serves many concurrent requests — this is why continuous batching is the single highest-leverage serving optimization.
- **What kernel fusion changes.** Naive attention materializes S = QKᵀ (N×N), writes it to HBM, reads it back for softmax, writes it again for the multiply with V: three extra N²-scale HBM round trips, and the N² matrix itself can exceed SRAM many times over. FlashAttention tiles Q, K, and V into blocks sized to fit in SRAM, computes scaled dot-product attention per tile, and maintains a running softmax normalization (online softmax: keep the running max m and sum ℓ, rescale as new tiles arrive) so the output is accumulated incrementally. Result: exact same numbers, HBM traffic drops from O(N²) to O(N²·d²/M) where M is SRAM size — the paper's Theorem 2 — and memory drops from O(N²) to O(N) (arXiv:2205.14135, 2022). The general lesson: fusion converts HBM traffic into SRAM traffic, which is the only way to beat the bandwidth wall without changing the math.
- **What capacity buys you in serving.** HBM capacity sets three budgets: (1) model size — weights must be resident for latency-free decode, so one H200 (141 GB) holds a 70B FP16 model (~140 GB) barely, while one MI300X/B200 (192 GB) holds it with room for KV cache or a larger quantized model; (2) KV cache — per token, KV cache ≈ 2 × layers × kv_heads × head_dim × bytes per element per sequence; long contexts and high concurrency eat GB quickly, and cache exhaustion, not compute, caps batch size; (3) batch size — spare HBM after weights is the KV-cache budget that continuous batching fills. Host RAM/NVMe tiers enable weight streaming and offload (e.g., DeepSpeed-Inference-style offload), but each tier crossing costs an order of magnitude in bandwidth and shows up directly in TTFT and TPOT.

## Harness angle
When your agent harness sees TPOT collapse under load, the fix is usually not more FLOPS but more HBM bandwidth or more KV-cache headroom — so the harness should expose concurrency and context-length limits to the serving layer as explicit, tunable contracts rather than retrying blindly: a well-placed max-concurrent-requests or context-trimming policy keeps the KV cache inside HBM and preserves TPOT for everyone, while a naive "retry on 429" loop just moves the queue.
