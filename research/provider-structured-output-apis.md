# Structured-output API surfaces per provider (OpenAI, Anthropic, Gemini, DeepSeek) — a 2026 snapshot
researched: 2026-08-27 · researcher: glm-5.3-flash

## Key facts
- OpenAI Structured Outputs (`response_format: {type: "json_schema", strict: true}`, available in Chat Completions since the August 2024 announcement and in the Responses API as `text.format`) constrains decoding so output conforms to the supplied JSON Schema; OpenAI's launch announcement reported 100% schema adherence on tests vs. <40% for prompting alone (OpenAI announcement, retrieved 2026-08-27). Treat the 100%/40% figures as the vendor's own 2024 eval, not an independent benchmark.
- OpenAI strict-mode hard constraints (OpenAI API docs, retrieved 2026-08-27): every field must be listed in `required` (emulate optional via union with `null`, e.g. `"type": ["string", "null"]`); `additionalProperties: false` must be set on all objects; root must be an object (no root `anyOf`); unsupported keywords (`allOf`, `not`, `if`/`then`/`else`, `dependentSchemas`, `dependentRequired`) cause an API error rather than being ignored.
- OpenAI schema size limits (OpenAI API docs, retrieved 2026-08-27): up to 5,000 object properties, up to 10 levels of nesting, ≤120,000 total characters of names/enums/consts, ≤1,000 enum values (single string enums >250 values limited to ≤15,000 total enum characters). Fine-tuned models additionally reject `minLength`/`maxLength`/`pattern`/`format`, numeric bounds, `patternProperties`, and array item-count limits.
- OpenAI output ordering: "outputs will be produced in the same order as the ordering of keys in the schema" (OpenAI API docs, retrieved 2026-08-27). Community-reported corollary — the first property in `properties` must also be first in `required` — is not stated on the current docs page; treat it as an operational folklore rule, hedged, not a documented guarantee.
- OpenAI also supports strict schemas for function/tool calling: `strict: true` inside the tool definition guarantees tool arguments match the schema; OpenAI states it works for all models supporting tools, `gpt-4-0613` and `gpt-3.5-turbo-0613` and later (OpenAI announcement, retrieved 2026-08-27).
- JSON mode (`response_format: {type: "json_object"}`) guarantees only syntactic validity, not schema conformance, and (OpenAI docs) requires the word "json" in the prompt.
- Anthropic: no json_mode flag. Guarantees come from two surfaces — strict tool use (`strict: true` on a tool, which "guarantees schema validation on tool names and inputs") and JSON outputs (`output_config.format`, previously the `structured-outputs-2025-11-13` beta's `output_format`; the beta header is still accepted) (Anthropic Claude Platform docs, retrieved 2026-08-27). `tool_choice` values: `auto` (default), `any` (must call at least one tool), `tool` with a name (must call that tool), `none`, plus `disable_parallel_tool_use: true` (Anthropic cookbook/skills docs, retrieved 2026-08-27).
- Google Gemini: set `response_format`/generationConfig `responseMimeType: "application/json"` plus `responseSchema` (OpenAPI 3.0 subset). Gemini supports only a JSON-Schema subset (types: string, number, integer, boolean, object, array, null) and "ignores unsupported properties" instead of erroring — unlike OpenAI (Google AI docs, retrieved 2026-08-27).
- Gemini property ordering: docs state outputs appear "in the same order as the keys in the schema"; Gemini 2.0/Flash-Lite era models required an explicit `propertyOrdering` list, while 2.5+ models no longer do (Google AI docs, retrieved 2026-08-27). Enum mode (an enum-only schema with `responseMimeType: text/plain`) is documented in the Firebase structured-output guide (retrieved 2026-08-27); the core docs page emphasizes enums inside JSON schemas for classification.
- DeepSeek: Chat Completions `response_format: {type: "json_object"}` "guarantees the message the model generates is valid JSON" — JSON mode only, no schema enforcement in Chat Completions; requires "json" in the prompt, an in-prompt format example, and a sensible `max_tokens` (else the model "may generate an unending stream of whitespace" until the token limit) (DeepSeek API docs, retrieved 2026-08-27). A third-party guide (chat-deep.ai, retrieved 2026-08-27) describes a Responses API accepting `text.format` with `type: "json_schema"` on DeepSeek models — plausible but not confirmed on DeepSeek's own docs; hedge accordingly.

## How it works
The mechanism differs by provider, and that difference is the whole point. OpenAI's strict mode is constrained decoding: the model's token-by-token sampling is restricted to a grammar derived from your schema, so syntactic schema violations are impossible at generation time, not merely discouraged. Anthropic's strict tool use guarantees the tool name and input schema validate (schema-conformance for tool inputs); its newer `output_config.format` JSON outputs extend typed output beyond tool calls. Gemini's responseSchema is also enforced at generation time against a subset of the spec, but unsupported schema fields are silently ignored — so a schema keyword Gemini doesn't implement won't error, it just won't constrain anything. DeepSeek's json_object is the weakest guarantee: it constrains the output to *parse* as JSON; the *shape* is whatever your prompt example nudged the model toward, so field names, types, and nesting can drift between calls.

Worked example of the guarantee gradient for extracting `{"name": string, "age": integer}`:
1. **OpenAI strict**: schema `{"type":"object","properties":{"age":{"type":"integer"},"name":{"type":"string"}},"required":["age","name"],"additionalProperties":false}`. Output is guaranteed to parse AND match this schema. To make `age` optional you must use `"type": ["integer","null"]` and keep `age` in `required` — the doc rule that most surprises newcomers. Note key order in output follows schema key order, so putting `age` first in `properties` yields `{"age":...,"name":...}`.
2. **Anthropic**: define a tool `extract_person` with the same input schema and `tool_choice: {"type":"tool","name":"extract_person"}`; the model must emit a tool_use block whose input validates against the schema. With `tool_choice: {"type":"any"}` you force *some* tool; the model can still pick among them.
3. **Gemini**: `responseMimeType: "application/json"` + `responseSchema: {type:"OBJECT", properties:{name:{type:"STRING"}, age:{type:"INTEGER"}}, required:["name","age"]}`. Valid at generation time; if you'd used `minLength` on `name`, Gemini would ignore it rather than enforce it.
4. **DeepSeek**: `response_format: {"type":"json_object"}` + prompt "Respond in JSON like {"name": "Alice", "age": 30}". You get valid JSON; nothing stops `{"full_name": ...}` or `age: "thirty"` on a later call. Local validation is mandatory.
What none of them guarantee: semantic correctness (right values, not just right shape), content beyond a truncation cutoff, or business rules inside the values — schema enforcement ends at structure.

## Harness angle
A harness should not treat "the provider has structured outputs" as one boolean. Config should encode a per-provider guarantee tier — OpenAI strict / Anthropic strict tool / Gemini responseSchema / DeepSeek json_object — and wire a validator + retry-with-error-feedback path only for tiers below full schema enforcement (Gemini's ignored-keyword trap and DeepSeek's JSON-only mode both need it). Forcing via `tool_choice: any` vs `tool` on Anthropic is a distinct harness decision: `any` lets the model route between extractors; `tool` is the deterministic single-extractor equivalent of OpenAI's `strict` response_format.
