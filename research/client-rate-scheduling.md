# Client-Side Scheduling Under Provider Rate Limits: Concurrency Caps, Adaptive Throttling, and Pacing
researched: 2026-08-27 · researcher: glm-5.3-flash

## Key facts
- Queueing theory: average response time ≈ ServiceTime / (1 − Utilization); response time **doubles at 50% utilization** and explodes non-linearly as utilization approaches 100% (Practical Insights From Queueing Theory / USENIX SREcon24 "Queues and You" slides, retrieved 2026-08-27). Every halving of idle time doubles expected residence time — going 50%→75% utilization moves residence from 2× to 4× service time (USENIX SREcon24 slides, retrieved 2026-08-27).
- M/M/1 latency: W = 1/(μ − λ); latency → ∞ as λ → μ. Rule of thumb from practice: keep utilization off the "knee," roughly 70–80% (semicolony.dev queueing-theory guide, retrieved 2026-08-27). Little's Law ties concurrency = throughput × latency, so runaway latency silently inflates in-flight requests too.
- Google SRE adaptive throttling: each client tracks `requests` and `accepts` over (at least) the last two minutes and rejects a fraction locally, without hitting the network, with probability = max(0, (requests − K·accepts) / (requests + 1)); Google found K = 1.1 (i.e., allow traffic 10% above the recent success rate) works well in practice (Google SRE Book, "Handling Overload," retrieved 2026-08-27).
- Apache Beam ships a production implementation of the SRE adaptive throttler (`AdaptiveThrottler`), including a target-minimum request rate per sample period so probabilistic throttling never cuts traffic to exactly zero (Apache Beam 2.74.0 docs, retrieved 2026-08-27).
- OpenAI Python SDK: retries **2 times by default** (3 total attempts) on connection errors, 408, 409, 429, and ≥500, using short **exponential backoff with jitter**; configurable via `max_retries` on the client or per-request (openai-python README, retrieved 2026-08-27).
- LiteLLM Router: retries 429s automatically; default retry count for the `completion` path is **2 retries (3 total attempts)** per the LiteLLM retries docs, with fixed + exponential backoff options; the Router constructor exposes `num_retries`, `timeout`, and `default_max_parallel_requests` to cap concurrency per deployment (LiteLLM docs / litellm/router.py, retrieved 2026-08-27).
- LiteLLM cooldown behavior: deployments that return rate-limit errors are put into cooldown and traffic is routed elsewhere; when *all* deployments of a model are in cooldown, LiteLLM raises `RouterRateLimitError` ("No deployments available... try again in X seconds"). As of issue #27823 (retrieved 2026-08-27) this error historically lacked a `Retry-After` header — a real client-side scheduling hazard because downstream callers cannot programmatically learn the wait time.
- LiteLLM `enforce_model_rate_limits`: with this flag, `rpm`/`tpm` set per deployment become hard limits and requests over the limit are blocked with a local 429 *before reaching the provider* — client-side throttling implemented in the gateway (LiteLLM proxy load-balancing docs, retrieved 2026-08-27). In production, LiteLLM tracks cooldown state and tpm/rpm usage in Redis across proxy replicas (LiteLLM routing docs, retrieved 2026-08-27).
- AWS SDKs: "standard" retry mode (the default in most SDKs) uses exponential backoff **with jitter**; "adaptive" mode adds a client-side rate-limiting token bucket on top of standard retries, using a virtual-clock rate estimator (AWS SDK retry behavior docs + AWS Developer Tools Blog, retrieved 2026-08-27). AWS's 2015 "Exponential Backoff and Jitter" post showed (by simulation) that "full jitter" (sleep = random(0, min(cap, base·2^n))) beats equal-jitter and no-jitter backoff for completion time under contention (AWS Architecture Blog, retrieved 2026-08-27).
- Boto3 exposes the adaptive mode via `retry_mode = "adaptive"` in its config (Boto3 retries docs, retrieved 2026-08-27).

## How it works
The core mechanism is queueing: provider limits turn your client into a queue in front of a server with fixed service capacity. As offered load (your concurrency) approaches capacity, M/M/1 queueing predicts latency ~1/(μ−λ): at 50% utilization latency is already ~2× service time; at 90% it is ~10×; at 99% ~100×. So the *real* lever is not retry tuning but capping concurrency so the system stays off the knee (~70–80% of capacity).

**Client token bucket / leaky bucket.** A counter of "tokens" refills at rate r (tokens/sec), up to burst capacity b; each request consumes tokens, and requests that would drive the counter below zero are held in a client-side queue. The leaky-bucket view is equivalent: the queue drains at a fixed rate r. This converts provider RPM/TPM limits into a client-side meter, so most 429s never leave the process. LiteLLM's `enforce_model_rate_limits` + Redis-based tpm/rpm tracking is exactly this pattern at the gateway tier.

**AIMD / adaptive throttling (Google SRE).** Keep a two-minute window of `requests` sent and `accepts` received. If requests outpace accepts by more than factor K, reject the excess *locally* with probability:

  reject_prob = max(0, (requests − K·accepts) / (requests + 1))

Worked example (K = 1.1, per the SRE book): a client sent 1,000 requests in the last window and only 600 were accepted (provider returned 429 for 400). Then requests − K·accepts = 1,000 − 660 = 340, and reject_prob = 340/1,001 ≈ 34%. About a third of new calls fail instantly in the client, cutting offered load toward the rate the provider is actually accepting, without wasted network round-trips or retry storms. As accepts recover, the probability decays automatically — additive-up/additive-down behavior emerges from the sliding window. Beam's `AdaptiveThrottler` adds a floor so some requests are always tried. AWS's adaptive retry mode implements the same idea as a variable-rate token bucket driven by a client-side rate estimator (it halves capacity on throttling, doubling on success — AIMD at the token level).

**Pacing a 10k-request fanout.** Instead of firing 10k concurrent calls and letting retries absorb the 429 storm: (1) derive steady rate from the limit, e.g., a 900k-TPM tier with ~500-token calls ⇒ pace at ~30 requests/s; (2) enforce with a semaphore (concurrency cap ≈ Little's Law: throughput × target latency) plus a token bucket for the burst allowance; (3) apply **full jitter** to spacing (AWS's simulation-backed result) so thousands of clients don't synchronize their retry clocks into thundering herds; (4) let the adaptive throttler trim the rate if accepts fall. At 50% of provider capacity the queueing formula predicts ~2× service time; at 99% it predicts ~100× — pacing is the difference between a fanout that finishes in minutes and one that collapses into retry storms.

## Harness angle
A harness should never hand a raw 10k-item fanout to an SDK's default retry loop (2 retries with short backoff is designed for stragglers, not sustained overload — per openai-python README, retrieved 2026-08-27). The concrete decision: put a semaphore-bounded concurrency cap + SRE-style adaptive throttler *in front of* the model client, sized from the provider's documented RPM/TPM, with full-jitter pacing — and treat `RouterRateLimitError`-style errors without `Retry-After` headers as a signal to expose the cooldown time to the caller rather than blind-retrying.
