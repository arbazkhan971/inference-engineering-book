# Arithmetic intensity and the roofline model: why prefill saturates FLOPs and decode starves on bandwidth
researched: 2026-08-27 · researcher: glm-5.3-flash
## Key facts
- Arithmetic intensity (AI) of an operator = FLOPs executed per byte of memory traffic (FLOP/byte). It is a property of the *workload + batch size*, not the chip (Williams et al., ACM CACM 2009, roofline paper).
- Roofline: attainable performance = min(peak compute FLOP/s, peak bandwidth × arithmetic intensity). Plot FLOP/s (y) vs AI (x, log-log): a bandwidth *slope* on the left, a flat compute *ceiling* on the right; the knee is the machine balance point = peak FLOP/s ÷ peak bytes/s (Williams et al., 2009).
- NVIDIA H100 SXM: FP16/BF16 tensor 1,979 TFLOPS and FP8 3,958 TFLOPS *with 2:4 sparsity* (i.e., 989.5 / 1,979 TFLOPS dense); 80 GB HBM3 at 3.35 TB/s (NVIDIA H100 product page, fetched 2026-08-27).
- H100 SXM machine balance ≈ 989.5e12 ÷ 3.35e12 ≈ **295 FLOP/byte** (BF16 dense), or ~1,480 FLOP/byte at FP8 dense (computed from NVIDIA H100 page values above, 2026-08-27). Any kernel with AI below that ridge point cannot reach peak FLOPs.
- NVIDIA H200 SXM: 141 GB HBM3e at 4.8 TB/s; NVIDIA markets ~4 petaFLOPS (FP8, sparse) of transformer-engine compute — 1.4× the H100's bandwidth with the same Hopper compute (NVIDIA H200 datasheet, fetched 2026-08-27). That *lowers* the ridge point to roughly 210 FLOP/byte (BF16 dense), a machine tuned to move decode traffic.
- NVIDIA HGX B200 (Blackwell, SXM6): BF16/FP16 tensor 2.25 PFLOPS dense (4.5 sparse), FP8 4.5 PFLOPS dense (9 sparse), 180 GB HBM3e at 7.7 TB/s, 1,000 W TGP (Lenovo HGX B200 spec sheet citing NVIDIA, LP2226, fetched 2026-08-27). Ridge point ≈ 2,250e12 ÷ 7.7e12 ≈ **292 FLOP/byte** (BF16 dense) — near-identical balance to H100, but 2.3× both axes.
- AMD Instinct MI300X: 1.3 PFLOPS peak FP16/BF16 (2.61 PFLOPS with structured sparsity), 192 GB HBM3, 5.3 TB/s peak memory bandwidth (AMD MI300X product page/data sheet, fetched 2026-08-27). Ridge point ≈ 1,300e12 ÷ 5.3e12 ≈ **245 FLOP/byte** (FP16 dense) — the most bandwidth-tilted of the three, which is why MI300X is marketed on large-model inference.
- Decode arithmetic intensity for a GEMV-like step: each generated token reads all weights once, ~2 FLOPs per weight parameter. For a 70B model in BF16 (2 bytes/param), AI ≈ 2 FLOP ÷ 2 bytes ≈ **1 FLOP/byte** per sequence at batch 1 — roughly 2 orders of magnitude below the ~245–295 FLOP/byte ridge points above, so decode runs deep in the bandwidth-bound region (formula standard; chip constants sourced above, 2026-08-27).
- Batching divides weight traffic per token: at batch B (same weights reused for B sequences), decode AI ≈ B FLOP/byte for BF16 — the ridge point of an H100 SXM (~295) is crossed at a batch of a few hundred, which is exactly when decode flips to compute-bound (derived from the formula and H100 page constants, 2026-08-27).
## How it works
- A transformer forward pass is matrix multiplies. A GEMM with matrices M×K and K×N does ~2·M·N·K FLOPs while touching ~(M·K + K·N + M·N)·bytes(weights in whatever precision). Big, reused tiles amortize memory reads: that's prefill. Decode processes one token at a time (M=1), so the GEMM degenerates toward GEMV: you stream the entire weight matrix from HBM to produce one tiny output. FLOPs per byte collapse; the SMs idle waiting on memory.
- To read a roofline chart: x-axis is arithmetic intensity (FLOP/byte, log scale), y-axis is attainable FLOP/s. Draw a diagonal line of slope = peak bandwidth (bytes/s × AI) and a horizontal line at peak FLOP/s. A kernel sits somewhere under this "roof"; its x position instantly tells you which resource is the limiter. The knee where the diagonal meets the ceiling is the ridge point = peak-FLOP/s / peak-bytes/s. Left of the knee: buying faster compute buys nothing; only more bandwidth, smaller weights (FP8/FP4), or more reuse per byte helps.
- Worked example (H100 SXM, BF16 dense): peak = 989.5 TFLOP/s, bandwidth = 3.35 TB/s. Ridge = 989.5/3.35 ≈ 295 FLOP/byte. Decode of a 13B BF16 model at batch 1: AI ≈ 1 FLOP/byte → ceiling ≈ 3.35e12 FLOP/s ≈ 3.35 TFLOP/s, i.e., <0.4% of peak compute; max decode speed ≈ 3.35e12 bytes/s ÷ 26e9 bytes ≈ ~129 tokens/s per sequence even with perfect kernels (constants from NVIDIA H100 page, fetched 2026-08-27). At batch 64, AI ≈ 64 → ~214 TFLOP/s of useful work from the same traffic.
- Batch size is the dial: prefill already sits right of the ridge (compute-bound, so engines batch prompt chunks to fill tensor cores); decode sits far left, and continuous batching slides it rightward — trading per-request latency (ITL) for aggregate throughput until the compute ceiling, KV-cache capacity, or TTFT SLO stops you.
## Harness angle
- Your SLO mix should pick your GPU class and batch policy: if your agent workload is mostly short-prompt/long-decode (agentic loops), bandwidth-per-FLOP (lower ridge point, e.g., H200/MI300X) and higher decode batch matter more than raw TFLOPS; conversely, if you're doing long-document prefill or heavy structured-output prompting, compute-rich SKUs pay off. Practically: cap decode batch where ITL×batch still meets your per-token SLO, because beyond the ridge point extra batch only inflates latency, not throughput.
