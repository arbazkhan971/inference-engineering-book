# How tool calls arrive over streaming APIs (OpenAI, Anthropic, Gemini)
researched: 2026-08-27 · researcher: glm-5.3-flash

## Key facts
- **OpenAI Chat Completions** streams tool calls as `choices[].delta.tool_calls[]` entries. The first delta for a call carries `index`, `id`, `type: "function"`, and `function.name`; subsequent deltas for the same call carry only `index` plus a `function.arguments` **string fragment**. Assembler must buffer by `index` and concatenate fragments. `finish_reason: "tool_calls"` on the final chunk signals the batch of calls is complete (OpenAI docs, fetched 2026-08-27; Azure OpenAI docs confirm `finish_reason: tool_calls` means "the model called a tool", fetched 2026-08-27).
- **OpenAI Responses API** replaces the index array with typed SSE events: `response.output_item.added` (opens a function-call item with `id`, `name`, empty `arguments`), then a series of `response.function_call_arguments.delta` events carrying `response_id`, `item_id`, `output_index`, and `delta` (a string fragment), then `response.function_call_arguments.done` and `response.output_item.done` carrying the complete item. Accumulation is by `item_id`/`output_index`, e.g. `final_tool_calls[index].arguments += event.delta` (OpenAI function-calling guide, Responses streaming section, fetched 2026-08-27).
- Example Responses delta from the docs: `{"type":"response.function_call_arguments.delta","response_id":"resp_1234xyz","item_id":"fc_1234xyz","output_index":0,"delta":"location"}` (OpenAI docs, fetched 2026-08-27).
- **Anthropic Messages API** streams each tool call as a content block: `content_block_start` with a `tool_use` block (`id` like `toolu_01T1x1fJ34qAmk2tNTrN7Up6`, `name`, `input: {}`), then `content_block_delta` events of type `input_json_delta` whose `partial_json` field carries **raw string fragments of the JSON-serialized input** — e.g. `"{\"location\":"`, `" \"San"`, `" Francisc"`, `"o,"`, `" CA\"}"`. The stream may begin with `partial_json: ""` (Anthropic streaming docs, fetched 2026-08-27).
- Anthropic closes the block with `content_block_stop` — the docs state it is only after this event that the accumulated string can safely be parsed as JSON — and the message ends with `message_delta` carrying `stop_reason: "tool_use"` (Anthropic streaming docs, fetched 2026-08-27).
- Anthropic notes current models emit **one complete key/value property per delta**, so gaps between deltas are expected, not a stall; chunking exists to support finer granularity in future models (Anthropic streaming docs, fetched 2026-08-27).
- **Google Gemini**: classic `streamGenerateContent` delivers `functionCall` parts, where `FunctionCall.args` is a JSON **object** (not a string) and the model can signal `MALFORMED_FUNCTION_CALL` when the generated call is invalid (Gemini API reference, fetched 2026-08-27). The current function-calling docs' "Stream tool calls" section describes the Interactions/Live-style events: `step.start` gives call `id`, `name`, initial `arguments`; `step.delta` carries `partial_arguments`/`arguments` deltas that the client **must aggregate** to reconstruct complete calls before executing (Gemini function-calling docs, fetched 2026-08-27). Gemini supports parallel function calls (multiple `functionCall` parts, `tool_choice: "any"`).
- **Arguments are strings at OpenAI and Anthropic, objects at Gemini** — OpenAI `function.arguments` and Anthropic `partial_json` are UTF-8 string fragments that must be concatenated then `json.loads`-ed; Gemini's `args` arrives as a structured object, so no string-assembly/escape handling is needed there (provider docs, fetched 2026-08-27).
- **Empty arguments**: a no-parameter call may stream the empty string, yielding `arguments == ""` at OpenAI — the normalizer must treat `""` as `{}` rather than erroring; Anthropic's `partial_json` may be `""` for one or more deltas; Anthropic's `tool_use.input` is guaranteed to be an object at completion (provider docs, fetched 2026-08-27).
- **Interleaving**: all three providers can emit multiple tool calls per turn; OpenAI Chat identifies them by `index`, Responses by `output_index`/`item_id`, Anthropic by content-block `index` and distinct `toolu_` ids. Providers do not interleave fragments of two different calls within one Chat Completions delta index, but multiple indices can arrive back-to-back, and text and tool-call deltas may mix (OpenAI/Anthropic docs, fetched 2026-08-27).
- **Engine side**: vLLM's OpenAI-compatible server reconstructs this format from raw model text via per-model `ToolParser.extract_tool_calls_streaming()` parsers (hermes, llama3_json, mistral, pythonic, etc.), and its own docs warn that without strict tool calling the parsed "arguments may occasionally be malformed or violate the function's parameter schema" (vLLM docs, fetched 2026-08-27) — i.e., malformed streamed JSON is an expected failure mode, not an anomaly.

## How it works
All three wire formats solve the same problem — the model emits tool arguments token by token, so the API must ship you a byte-stream that a client can reassemble into one JSON object per call — but they pick different keys for "which call does this fragment belong to."

In **OpenAI Chat Completions**, every streamed chunk has `choices[0].delta`; when the model is calling tools, that delta carries a `tool_calls` array. Each entry has an `index` naming the call slot (0, 1, … for parallel calls). The id and function name appear once; afterward you get bare `{index, function: {arguments: "<fragment>"}}` entries. The arguments value is a JSON *string*, so fragment boundaries can split escape sequences, keys, or surrogate pairs — you must concatenate before parsing, never parse per-chunk. The stream ends with `finish_reason: "tool_calls"`.

The **Responses API** makes the same thing event-typed: an `output_item.added` opens the item, `function_call_arguments.delta` streams the string, `done` events close it. This is friendlier — you key accumulation on `item_id` instead of a positional index — but the payload discipline is identical.

**Anthropic** pushes the string-ness one level deeper: the tool call is a content block (`index`-addressed, like any other block), and what streams is `partial_json` — fragments of the serialized `input`. Concatenation order is guaranteed by stream order; parse only after `content_block_stop`. Because the model emits whole key/value pairs per delta, a partial-JSON parser (e.g. Pydantic-style tolerant parsing) is needed only if you want to surface arguments as they arrive.

**Gemini** historically sidestepped string assembly: `functionCall.args` is a real object inside the streaming chunk, and the newer streaming surface (`step.start`/`step.delta` with `partial_arguments`) still requires client-side aggregation. Failure modes to defend against in a normalization layer: dropped or out-of-order SSE frames leaving a truncated JSON string; malformed partial JSON (vLLM explicitly warns its text-derived parsers can emit schema-violating arguments); index/key resets mid-stream (new turn reusing index 0 before the previous call closed); empty-string arguments that must coerce to `{}`; and splitting a chunk mid-escape, which corrupts naive incremental parsers.

## Harness angle
Build one internal `ToolCallAccumulator` keyed by a provider-agnostic call id (Chat `index`→`id`, Responses `item_id`, Anthropic `block index`+`toolu_` id, Gemini `step.start` id): concatenate string fragments, parse JSON exactly once at `stop`/`finish_reason: "tool_calls"`/`stop_reason: "tool_use"`, coerce `""`→`{}`, and route parse failures to a retry-with-error tool result rather than crashing the loop — because engines like vLLM legitimately produce malformed streamed arguments.
