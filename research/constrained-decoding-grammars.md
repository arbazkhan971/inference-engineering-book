# Constrained / Grammar Decoding Mechanics (FSMs, CFGs, logit masking, and the major engines)

researched: 2026-08-27 · researcher: glm-5.3-flash

## Key facts

- **Core mechanism**: constrained (grammar) decoding builds a machine (finite-state automaton for regexes, pushdown automaton for context-free grammars) over *token ids*, not characters. At every generation step the engine is in a state; the set of tokens whose continuations the grammar still accepts is computed, all other logits are masked to −inf before sampling, so the sampled token can never violate the grammar — validity is guaranteed *by construction*, not statistically. (Outlines paper, arXiv:2307.09702, retrieved 2026-08-27; XGrammar paper, arXiv:2411.15100, retrieved 2026-08-27)
- **Outlines** (dottxt-ai) popularized FSM-based guided generation: it compiles a regex/schema into an FSM and indexes the model's vocabulary so each state maps to an allowed-token mask. Model-agnostic; integrated into vLLM, Ollama, llama.cpp, TGI. (arXiv:2307.09702, retrieved 2026-08-27; outlines repo, retrieved 2026-08-27)
- **XGrammar** (MLC, Nov 2024) speeds up general CFGs via an "adaptive token mask": it precomputes which vocabulary tokens are context-independent (always/never allowed given a grammar rule), keeps a persistent pushdown execution stack across steps, and overlaps grammar computation on CPU with the GPU forward pass. Paper claims up to **100x reduction in per-token grammar-processing latency** for CFGs vs prior state of the art, and up to **80x end-to-end serving speedup** on structured-output workloads with Llama-3.1 on an **NVIDIA H100** (and masking benchmarks on Llama-3-8B with an AMD 7950X CPU + RTX 4090 / H100 GPU). (XGrammar paper arXiv:2411.15100 and MLC blog, 2024-11-22, retrieved 2026-08-27)
- **XGrammar masking-speed specifics**: on logit-masking benchmarks it outperforms existing solutions by up to **3.5x on JSON-schema workloads and up to 10x on CFG-guided generation**; XGrammar-powered serving beats existing engines by up to **14x for JSON-schema generation** and up to **80x for CFG-guided generation** (Llama-3, H100). (MLC blog, 2024-11-22, retrieved 2026-08-27)
- **vLLM integration, dated**: vLLM PR #10785 (merged Dec 2024) added XGrammar and made it the default backend for JSON/grammar guided decoding. Measured on its benchmark run: **0.94 req/s, 480.27 output tokens/s, 100% correct rate**, mean time-to-first-token ≈ **4552 ms** with XGrammar vs **0.22 req/s, 113.31 output tokens/s** with the Outlines backend — roughly a **4x throughput gap**, with Outlines' mean first-token latency ≈ **38.5 s** driven by FSM compilation. (vLLM PR #10785, retrieved 2026-08-27)
- **vLLM blog (2025-01-14)**: switching structured-decoding backend to XGrammar brought **up to 5x improvement in time-per-output-token (TPOT) under load**; the v1 engine moved to schedule-level mask computation/broadcasting so batches mix free-form and guided requests efficiently. As of current vLLM docs, supported backends are **xgrammar and guidance (llguidance)**, with the old `guided_*` API fields removed in v0.12.0 in favor of `StructuredOutputsParams`. (vLLM blog 2025-01-14 and docs.vllm.ai structured outputs page, retrieved 2026-08-27)
- **Guidance / llguidance** (guidance-ai, re-design of Microsoft's 2023 Guidance parser, written in Rust) computes a token mask in **about 50 μs of CPU time per token for a 128k vocab**, with negligible startup cost; on the MaskBench JSON-schema benchmark other libraries were reported as roughly 10–1000x slower (author-measured). It powers guidance, llama.cpp, SGLang, vLLM, mistral.rs, onnxruntime-genai, and Chromium. (guidance-ai/llguidance repo and "LLGuidance: Making Structured Outputs Go Brrr" blog, retrieved 2026-08-27)
- **Synapse / toktrie lineage**: Microsoft's constrained-decoding stack (Guidance → llguidance → Synapse) is built on **toktrie**, a Rust prefix-tree (trie) over the whole tokenizer vocabulary used to map string/byte constraints to allowed token-id sets quickly. (microsoft/toktrie repo, retrieved 2026-08-27)
- **TensorRT-LLM** supports guided decoding with **two grammar backends: XGrammar (JSON schema, regex, EBNF)** and an (Outlines-based) fallback, plus a documented workflow combining guided decoding with speculative decoding (CPU grammar check overlapped with GPU draft/verify). (TensorRT-LLM guided-decoding docs and NVIDIA tech blog #12, retrieved 2026-08-27)
- **Compilation overhead is the tax**: with the Outlines backend in vLLM, an FSM had to be built per request at token level, producing multi-second to tens-of-seconds time-to-first-token (e.g. the ≈38.5 s mean TTFT measured in PR #10785); XGrammar/llguidance reduce compile time and cache context-independent token sets to bring masking near zero overhead. (vLLM PR #10785 and vLLM blog 2025-01-14, retrieved 2026-08-27)

## How it works

1. **Compile the grammar.** A JSON schema / regex / EBNF grammar is converted to an automaton. Regular languages yield a finite-state machine; general CFGs (needed for nested JSON, code) yield a pushdown automaton with a stack. This is done over *characters*, then intersected with the tokenizer's vocabulary (via a token trie) to get, for each automaton state, the set of legal token ids.
2. **Per step: mask, then sample.** The model runs a forward pass and emits a logit vector of size |vocab| (e.g. ~128k). The engine looks up the current automaton state, gets the allowed-token mask, sets all other logits to −inf, then applies normal sampling (temperature/top-k/top-p operate on the surviving tokens). The chosen token advances the automaton state. Because every sampled token was in the allowed set, the completed output is always accepted by the grammar — no retries, no post-hoc validation.
3. **Making it fast.** Naively, computing the allowed set each step requires walking the grammar against every vocab token — the bottleneck Outlines hit at scale. XGrammar splits the vocabulary into context-independent tokens (precomputed once per grammar rule) vs context-dependent ones checked per step, keeps a persistent execution stack so no state is recomputed, and overlaps this CPU work with the GPU forward pass; llguidance/Synapse use a Rust parser plus the toktrie token trie to push per-step masking to ~50 μs.
4. **Worked example (from vLLM PR #10785, retrieved 2026-08-27):** same JSON-schema workload, same engine — Outlines backend: 0.22 req/s, 113 output tokens/s; XGrammar backend: 0.94 req/s, 480 output tokens/s, both at 100% correctness. So per-request decode time drops ≈4.2x purely from cheaper grammar compilation and masking, with identical structural guarantees.

## Harness angle

In any harness that needs machine-readable tool-call arguments, choose a serving engine with a compiled-grammar backend (XGrammar or llguidance) and enforce schemas server-side (`structured_outputs` params in vLLM, XGrammar backend in TensorRT-LLM) instead of client-side "please return JSON" prompting plus retry loops: you get guaranteed-valid tool calls and remove the multi-second-to-tens-of-seconds first-token penalty that per-request FSM compilation (the naive Outlines path) imposes under load.
